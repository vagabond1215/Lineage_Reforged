## User-approved multiple-tab policy and deferred gameplay gate (2026-11-12)

- **Tab state is not a session singleton.** Tab A logging out or signing into another account changes its own presentation/persistence preference; it is not an instruction to revoke Tab B's valid in-memory session for an otherwise unchanged retained account. Reset, delete, missing/invalid owner records and unsafe account lifecycle changes remain actual invalidation paths.
- **Shared identity, not synchronized view state:** for the same chosen account/Save, both tabs read the same owner-backed slot, campaign/continuity and accepted head. The World Library is intentionally unavailable in L1, so a durable world instance and its Save association must be contracted in L2. Do not invent tab-local world IDs or duplicate slots. If the player explicitly chooses different owned worlds/slots in later slices, keep those distinct; do not force one global Save per account.
- **Future world-driven live updates:** if and when an authoritative World service/coordinator exists, each subscribed tab receives ordered, versioned World state or committed deltas and automatically refreshes its **read-only view** on accepted changes. A shared Vite HTTP server or same-origin IndexedDB does not by itself provide a live World authority/push channel. A local-only implementation may use notification/invalidation plus authoritative IndexedDB readback, but that is not a remote World server and must not be described as one.
- **Future paused concurrent edits:** World pause is authoritative per World, not per tab; freezing simulation time does not freeze World revision or grant unlimited action credits. Mutating actions require authoritative serialized commit and an expected World/campaign/Save head. A paused-world action is either deliberately disallowed by the clock/action contract or committed under the same concurrency and time-cost rules as unpaused actions, never duplicated. If Tab A's command commits first, Tab B must apply a new authoritative update and must not submit its older in-flight edit blindly. On a true stale/conflicting pending edit, reject without publication or lost progress and show **“World progress changed. Reload this tab to continue.”**; reloading rereads the accepted World/Save/head. No silent last-writer-wins, automatic command retry, duplicate clock tick or duplicate side-effect.
- **Acceptance phasing:** automatic subscriber updates, authoritative pause ownership, serialized overlapping commands and clock progression need a functional gameplay slice. They are a **later gameplay/World coordinator gate**, not prerequisites for L1's unavailable Worlds placeholder. L1 must preserve existing Save revision/expected-head safeguards and never create tab-local parallel Save identities.
- **L1 witness boundary:** two-tab same-slot owner/readback consistency is desirable where the existing harness supports it; explicitly record NOT_RUN for a subcheck that depends on unavailable gameplay. Continue, Back and Logout remain nonpublication routes. A07 still covers genuine owner lifecycle invalidation, not ordinary cross-tab hint changes. Do not modify `CleanEpochAccountAdapter.validateSession` to enforce a singleton hint.
