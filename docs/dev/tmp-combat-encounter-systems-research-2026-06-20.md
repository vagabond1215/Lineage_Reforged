## 1. Executive Summary

The research pass examined combat, encounters, enemy archetypes, monster records, spawn profiles, tactical roles, tactics presets, equipment use-profiles, damage family mapping, conditions/status effects, injuries, death/defeat, loot, combat rewards, and combat-state boundaries.

The strongest recommendation is to treat combat as an authority-boundary problem before adding new combat schemas. Static content should define possible combat actors, encounter compositions, tactics defaults, loot envelopes, and condition definitions. Runtime should own current HP/MP/stamina, action queues, active statuses, injuries, death/defeat state, actual loot rolls, player combat state, NPC combat state, and encounter instances.

## 3. Current Repo-State Findings From Research

Research found or inferred the following current foundations:

- Static types define `MonsterRecord`, `EncounterTemplateRecord`, and `SpawnProfileRecord`.
- `MonsterRecord` includes identity, class, threat, summary, habitat/behavior tags, drops, loot, combat profile, default role, action packages, and difficulty scaling hooks.
- `EncounterTemplateRecord` lists monster ids, counts, roles, disposition, movement mode, regions, habitat tags, and encounter tags.
- `SpawnProfileRecord` ties encounter templates to regions, world hexes, settlements, sites, habitats, hazard pressure, density, hostility weighting, and movement modes.
- Tactical roles and tactics presets exist at the shared type level, including roles such as frontliner, disruptor, ranged pressure, healer, support buffer, debuffer/controller, opportunist, tank/protector, and flexible/adaptive.
- Combat runtime builds combatants from equipped items, item use-profiles, skills, abilities, spells, and titles.
- Runtime combat state tracks HP/MP/stamina resource pools, active status effects, action state, disposition, combatant kind, and temporary tactical overrides.
- Item records already define use-profiles, action ids, skills, effect channels, handling type, proficiency skill, combat tags, resolution hooks, target profile, and activation timing.
- Damage family is currently inferred from resolution hooks, spell school, ranged weapon skill, shield skill, item handling, or target disposition. No explicit damage-type enum was identified.
- Existing combat equipment audit work explicitly avoided adding static durability, item-instance logic, loot generation, magic runtime, or equipment compatibility changes.
- There is no complete static injury/wound/death/recovery authority identified by the research.

Codex must re-check these findings against the live checkout before permanent docs are written.

## 4. Current Gaps And Risks

### 4.1 Missing injury/wound model

There is no complete static injury, wound, or recovery profile authority. If future design needs bleeding, fracture, burns, poison, trauma, incapacitation, or persistent wounds, the first boundary must decide whether those are status effects, injury profiles, or future runtime-only state.

### 4.2 Death and defeat ambiguity

No clear content boundary currently defines death, nonlethal defeat, capture, retreat, surrender, corpse/loot behavior, companion death, or player defeat. This should remain runtime-owned until a deliberate decision exists.

### 4.3 Damage taxonomy ambiguity

The current runtime can infer melee/ranged/magic families, but a canonical static damage-type/defense-type taxonomy is not yet formalized. Future schemas must avoid duplicating equipment, spell, and combat hook meanings.

### 4.4 Tactics data vs AI runtime risk

Tactical roles and presets may become useful static content, but AI decision-making, target selection changes, forced roles, cooldowns, and turn-by-turn choices must remain runtime.

### 4.5 Loot and reward ambiguity

Monster records include drops and loot fields. Quest definitions/templates may include reward item references. There is not yet a single authority for combat loot tables, loot envelopes, or reward payout. Static content should not roll or pay rewards.

### 4.6 Encounter trigger ambiguity

Encounter templates and spawn profiles are good static foundations, but runtime spawning, travel encounter selection, quest-triggered fights, map triggers, event scheduling, and generated encounter instances need separate runtime/state owners.

### 4.7 NPC/faction/law consequences

Combat may involve guards, bandits, factions, civic law, witnesses, wanted state, and reputation consequences. Combat content must not mutate legal state, faction standing, social memory, or reputation.

## 5. Recommended Combat / Encounter Hierarchy

Recommended hierarchy:

```text
Combat Static Authorities
  -> Monster / Enemy Archetype
  -> Combat Role
  -> Tactics Preset
  -> Encounter Template
  -> Spawn Profile
  -> Status / Condition Definition
  -> Loot Table / Loot Envelope Descriptor

Cross-System Static References
  -> Item / Weapon / Armor / Use Profile References
  -> Spell / Ability / Skill References
  -> Quest / Trial / Event / Travel / NPC References

Runtime / Save State Later
  -> Combat Session
  -> Combatant Instance
  -> Current HP / MP / Stamina
  -> Current Position / Target / Action Queue
  -> Active Status Effects
  -> Injury / Defeat / Death State
  -> Actual Loot Rolls
  -> Player Combat History
```

## 6. Static Combat Authority Boundary

Static combat authority may own:

- monster/enemy identity;
- base combat profile descriptors;
- threat/difficulty bands;
- habitat and behavior tags;
- default tactical role;
- action package references;
- scaling hook descriptors;
- encounter composition descriptors;
- spawn-profile selection envelopes;
- tactics preset defaults;
- condition/status definitions;
- descriptive loot/drop envelopes.

Static combat authority must not own:

- current HP/MP/stamina;
- active statuses;
- action queues;
- current target;
- current position;
- current death/defeat state;
- injury progression;
- actual loot rolls;
- item grants;
- reward payout;
- player combat history;
- runtime encounter instance state;
- AI execution;
- pathfinding;
- UI state;
- storage state.

## 7. Monster / Enemy Archetype Boundary

A future monster/enemy archetype record may later own:

- id/slug/name/summary/status;
- monster class or enemy family;
- threat or difficulty band;
- habitat/behavior tags;
- base combat profile;
- default role;
- action package ids;
- difficulty scaling hooks;
- static loot/drop descriptors;
- sourceAuthorityNotes;
- notes.

It must not own runtime actor state, current resources, current target, current disposition changes, active effects, defeated/dead state, or rolled loot.

## 8. Encounter Template And Spawn Profile Boundary

Encounter templates should describe possible combat compositions. Spawn profiles should describe where and how encounter templates are selected. Neither should create encounter instances.

Encounter templates may later own:

- id/name/summary/status;
- disposition;
- movement mode;
- region/habitat tags;
- monster member references with min/max counts and role ids;
- allied template references if supported;
- difficulty band;
- notes.

Spawn profiles may later own:

- id/name/status;
- region/worldHex/settlement/site anchors;
- habitat tags;
- hazard pressure ranges;
- density bands;
- encounter weights;
- allowed movement modes;
- hostility weights;
- notes.

Runtime owns actual selection, spawn timing, position, generated actors, active encounter ids, and resolved outcomes.

## 9. Tactics And AI Boundary

Tactical roles and tactics presets can be static defaults.

Static records may define:

- role id;
- name;
- summary;
- preferred action types;
- default tactics;
- tactical preference weights;
- spell preferences;
- target preference rules;
- focus directives;
- tags.

Runtime owns:

- current forced roles;
- forced target ids;
- control mode changes;
- temporary AI suspension;
- actual action choice;
- turn-by-turn target selection;
- pathfinding and positioning.

## 10. Damage, Defense, Equipment, And Spell Boundary

Combat content can reference equipment and spell authorities, but should not duplicate their ownership.

Current item use-profiles and spell definitions already provide action/effect hooks. Future weapon/armor profile decisions must reconcile those hooks before combat schema work expands damage/defense metadata.

Static combat records may reference:

- item ids / item keys;
- use-profile action ids;
- skill ids;
- ability ids;
- spell ids;
- resolution hook ids;
- damage-family tags if later standardized.

Combat content must not:

- calculate damage;
- calculate mitigation;
- equip items;
- consume ammunition;
- mutate durability;
- execute spells;
- consume MP/stamina;
- grant skills;
- grant spell access;
- mutate inventory.

## 11. Conditions, Injuries, Wounds, And Recovery Boundary

The research recommends a static status/condition authority before separate injury profiles unless design requires greater detail.

Possible static `combat.status_effects` or future `combat.condition_profiles` records may own:

- id/slug/name/summary/status;
- tags;
- default duration descriptor;
- stack posture;
- resistance/removal descriptors;
- sourceAuthorityNotes;
- notes.

Runtime owns:

- active stacks;
- started/expires tick;
- magnitude;
- source actor;
- ongoing damage/healing;
- current wounds;
- recovery progress;
- death/defeat state.

Persistent injuries, recovery, disease, trauma, and long-term impairment should remain future decisions, not first-pass combat content.

## 12. Death, Defeat, And Failure Boundary

Death and defeat should remain runtime/gameplay state. Static content may later describe nonlethal or lethal posture, corpse eligibility, or defeat consequence descriptors, but must not decide or execute outcome state.

Future boundaries should separate:

- player defeat;
- NPC death;
- creature death;
- companion death;
- nonlethal incapacitation;
- surrender/retreat;
- capture;
- quest failure;
- loot availability;
- Chronicle entries;
- legal/faction consequences.

All mutation belongs to runtime, quest/event/civic/faction/NPC/social/Chronicle owners as applicable.

## 13. Loot, Rewards, And Combat Economy Boundary

Monster drops/loot and future loot tables should be descriptive. Runtime rolls and pays outcomes.

Static loot descriptors may own:

- item references;
- quantity min/max;
- chance/weight;
- rarity/context tags;
- source context;
- notes.

Static loot descriptors must not:

- roll outcomes;
- generate item instances;
- add inventory stacks;
- transfer ownership;
- pay currency;
- mark reward claimed;
- apply XP;
- mutate market value;
- write Chronicle entries.

Economy remains owner of market values, currency systems, transactions, and pricing.

## 16. Validation Direction

Future validators should eventually enforce:

1. strict records-only wrappers and id/slug consistency;
2. monster/enemy references resolve from encounter templates;
3. encounter-template references resolve from spawn profiles;
4. tactical role ids resolve to allowed roles;
5. tactics presets contain valid preference values and target rules;
6. action package, item, skill, ability, and spell references resolve where supported;
7. loot/drop item references resolve to canonical item keys or ids as selected by boundary decisions;
8. loot chances/weights are valid and not all zero;
9. encounter templates do not have empty member lists or invalid recursive references;
10. spawn profiles have coherent region/hex/settlement/site/habitat/hazard anchors;
11. monster base combat profiles are complete and non-negative;
12. condition/status definitions avoid runtime state fields;
13. no static combat content contains current HP/MP/stamina, active status instances, actor positions, action queues, current targets, death/defeat flags, injury progress, rolled loot, item grants, reward payout, legal/faction/reputation mutation, runtime, UI, storage, or gameplay execution fields.

## 17. Authored vs Generated Strategy

Fully authored:

- monster/enemy archetypes;
- encounter templates;
- spawn profiles;
- tactical roles;
- tactics presets;
- condition/status definitions;
- loot table definitions.

Generated once and saved later:

- possible scaled enemy variants;
- handcrafted encounter variants;
- named boss variants;
- placed encounter records if a future map/quest owner requires them.

Runtime/generated later:

- actual encounter instances;
- exact enemy counts/placement;
- action queues;
- current HP/statuses;
- actual loot drops;
- combat rewards;
- death/defeat outcomes;
- combat history.
