## Independent source conclusions

1. **Scoped compiled gate present:** `EpochApp.tsx` checks the exact native non-staging entry, `import.meta.env.PROD`, `MODE === 'world-owner-review'`, the compiled owner define, exact `127.0.0.1`/`localhost`, `/` or `/index.html`, plus exactly one `1` value for each of `welcomeL1`, `accountPresentation` and `worldPresentation`. The default normal production route remains the existing Classic UI. Ordinary DEV may display the reviewed Creator but never gets an owner Create callback. The owner still rejects writes outside the compiled loopback build/host.
2. **One account owner, not a second World store:** `Services` creates one `CleanEpochAccountStore` and one `CleanEpochAccountAdapter`; the UI passes the same adapter plus exact launcher session into the owner `createChronicleWorld` and `reopenChronicleWorld`. `validateWorldSession` requires its credential-issued `WeakMap` capability, owner instance identity and current account generation. A persisted login hint is read-only until password sign-in; no synthetic World authorization was added.
3. **World Library does not invoke the legacy campaign inventory on its own compiled review path:** `continueToWorlds` validates selected account, reads `listChronicleWorlds`, uses source/rules/scenario/generation checks from `projectWorldCard`, revalidates the session after awaits, and blocks corrupted inventory. The *existing* sign-in/bootstrap and compatibility launcher paths retain their old campaign recovery. That remains a coupling worth tracking, but no new World-entry Save recovery was introduced.
4. **Creation and uncertain acknowledgement are fail-closed:** The Creator normalizes the name, requires user confirmation, freezes the in-flight intent, disables unsupported settings and serializes duplicate submit. The app retains `accountId`, lifecycle `generation`, immutable intent/World IDs, name and original account revision in a ref across in-app navigation. It creates via atomic owner World + receipt; on any uncertain result it revalidates the session, reopens the authorized pair, lists a fresh World and compares World fields, receipt, projection fingerprint and full canonical source/rules. The Library receives a highlighted result only after this comparison. `initialize`, logout/reset and storage-change invalidation fence late UI results. On reload there is no frontend intent journal: the owner registry is consulted before any fresh create, so the existing committed World blocks a second distinct attempt. This is a bounded one-World pilot, not general multi-World support.
5. **Source code does not activate gameplay or family:** The UI has no Play/Open card action, does not fabricate a character, World-timed simulation, new Save, or World-to-Save linkage. Existing launcher compatibility remains explicitly reachable. PR #102's protected account store, adapter, pilot, source verifier and Vite files are inherited unchanged, with no v4 source manifest or protected pin edits.
