## What the intended player-facing UI is

Lineage is a **text-/systems-first tabletop and grand-strategy gameplay interface**, not an FPS/MMO combat HUD and not a flat dashboard of unrelated cards. The 2026-09-14 accepted direction in [UI Information Architecture Boundary, concept refinement](ui-information-architecture-boundary.md#22-concept-derived-gameplay-shell-direction) specifies:

- **Compact global top context:** lineage/character identity, date/turn/watch, relevant place/weather and global utilities; no developer metadata or every-resource strip.
- **Compact left character/navigation rail:** identity/portrait, bounded readiness, six existing domains (Character, World, Activity, Codex, Quests, Chronicle) and a dedicated Home/re-entry affordance rather than a seventh equal-height card.
- **One contextual main workspace:** a dominant map, scene, combat, record or activity surface; a right-side context inspector for selected target, status and owner-backed next actions; at most one related supporting notes/ledger/history strip. A combat surface may become the primary workspace without changing combat ownership or inventing a second clock.
- **Grounded fantasy visual grammar:** dark forest/charcoal framing with parchment/cream, grey, bronze, muted gold or silver; cartographic/archival materials and art that support orientation rather than obscure text. Avoid overwhelming single-hue wash, decorative dashboard sprawl or MMO-style chrome. Retain legibility, keyboard access, focus, small-screen reflow and reduced motion.
- **Truth before flourish:** what/where, current condition or objective, what changed, what is available next, its exact owner-supplied target/cost/phase/result and visible limits of knowledge.

This is the accepted *destination*. The currently implemented `InGameShell`, `WorldPanel`, `TopStatusBar` and read-only view-model work are transition sources, not final design authority. Do not merge the six domain owners, reimplement rules in React, build a global action registry or automatically expose future affordances.

## 2026-10-21 user-directed UI redesign priority and first route

**Priority selected:** UI usability and Character-first presentation now precede optional metabolic-reserve implementation. This updates *planning priority and player-facing composition*, not the accepted combat-result work or Game-version policy. The exact source-driven decision is [Gameplay UI Redesign: Character-First Priority, Shell Intent, And Incremental Migration](gameplay-ui-redesign-character-priority-and-first-migration-decision-2026-10-21.md); the prepared **non-installed** [Codex first-slice prompt](../dev/proposed-gameplay-ui-character-first-codex-prompt-2026-10-21.md) is a bounded Character presentation consumer. Both were prepared using live `master` `f56229dd` and require refresh against the actual runtime HEAD.

**Decisions now recorded for UI implementation sequencing:**

1. **Global shell** remains six-domain left rail, one top context strip and one main workspace; within the selected domain, sibling subsection navigation should be **horizontal directly beneath the top band**, with overflow/focus/reflow rather than a second permanent vertical rail. Home remains a separate compact re-entry affordance, not a seventh global nav domain or automatically enabled new action engine.
2. **Top resources/status** should use larger, accessible HP/MP/ST bars **without enclosing capsules** and meaningful **owner-backed** active condition/effect icons, not a persistent neutral `Condition: Stable` label. Do not invent icons/magnitudes from string-only effects or crowd out other identity/time/place context.
3. **Character Overview** is an identity/capability sheet, **not** Home/Current State. Show the real nine-attribute matrix (STR/DEX/AGI/CON/VIT/INT/WIS/SPT/CHA), compact skills/Echo/Growth, meaningful identity, a small gear preview and earned distinctions. Remove permanent readiness/recovery/general-system status sprawl, empty vanity counters, duplicated HP/MP/ST and technical `Runtime Bridge` data from player Overview.
4. **Attributes** no longer need an enormous mandatory separate page if accessible per-attribute detail and any future advancement owner survive. **Equipment** and **Inventory** remain separate task-focused destinations; Overview gets only a concise equipped-gear summary. A future Equipment compatible-item picker must route to existing item/equip owners.
5. **Nutrition is a deferred owner integration**: current `energyBalance` is daily rollover coverage, not a continuous signed balance; macro intake counters and quick/stored energy are **not** positive usable Carbs/Fat/Protein reserves. Preserve honest current hydration/condition information, but **omit the proposed composite Nourishment bars** until the [nutrition PR #6](https://github.com/vagabond1215/Lineage_Reforged/pull/6) and independent Human-normalized owner contract are implemented and validated. No UI mock values in gameplay.
6. **Migration sequence:** independent Character-first read-only UI slice → top-shell resource/status/layout slice → Equipment/Inventory refinement → World/combat presentation after actual engine-owned action-result disclosure → Home and remaining domains → selected-gameplay/accessibility/readback integration. One scoped consumer and acceptance matrix at a time.

**Sequencing caveat:** earlier [contextual architecture §8](contextual-player-action-and-command-architecture-decision.md#8-first-integration-and-later-loop) and older Home Game-version sequencing remain historical evidence. A new non-authoritative Character layout can precede Game promotion; **Home command activation** and engine-owned combat result disclosure have their own current owner/acceptance gates. The active `DEV-0.7.2.13` prompt controls its separate repair; this design branch does not replace it or claim a broad shell runtime implementation.
