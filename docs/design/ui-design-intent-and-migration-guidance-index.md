## What the intended player-facing UI is

Lineage is a **text-/systems-first tabletop and grand-strategy gameplay interface**, not an FPS/MMO combat HUD and not a flat dashboard of unrelated cards. The 2026-09-14 accepted direction in [UI Information Architecture Boundary, concept refinement](ui-information-architecture-boundary.md#22-concept-derived-gameplay-shell-direction) specifies:

- **Compact global top context:** lineage/character identity, date/turn/watch, relevant place/weather and global utilities; no developer metadata or every-resource strip.
- **Compact left character/navigation rail:** identity/portrait, bounded readiness, six existing domains (Character, World, Activity, Codex, Quests, Chronicle) and a dedicated Home/re-entry affordance rather than a seventh equal-height card.
- **One contextual main workspace:** a dominant map, scene, combat, record or activity surface; a right-side context inspector for selected target, status and owner-backed next actions; at most one related supporting notes/ledger/history strip. A combat surface may become the primary workspace without changing combat ownership or inventing a second clock.
- **Grounded fantasy visual grammar:** dark forest/charcoal framing with parchment/cream, grey, bronze, muted gold or silver; cartographic/archival materials and art that support orientation rather than obscure text. Avoid overwhelming single-hue wash, decorative dashboard sprawl or MMO-style chrome. Retain legibility, keyboard access, focus, small-screen reflow and reduced motion.
- **Truth before flourish:** what/where, current condition or objective, what changed, what is available next, its exact owner-supplied target/cost/phase/result and visible limits of knowledge.

This is the accepted *destination*. The currently implemented `InGameShell`, `WorldPanel`, `TopStatusBar` and read-only view-model work are transition sources, not final design authority. Do not merge the six domain owners, reimplement rules in React, build a global action registry or automatically expose future affordances.

## UI rework sequencing: open route decision, not an automatic rewrite

The user has raised the cost of continuing to test new systems through the legacy UI and asked for a consolidated design/migration route. This is a legitimate **priority-review trigger**, not by itself an approved change to the active executable prompt or an override of Game-version policy.

**Tension to resolve explicitly:** older [contextual architecture §8](contextual-player-action-and-command-architecture-decision.md#8-first-integration-and-later-loop) and [contextual index Route](contextual-player-command-architecture-index.md#route) place Home behind combat/selected victory and a separate Game-version decision; the more recent [Combat Skeleton First](combat-skeleton-first-priority-and-acceptance-boundary-decision.md#acceptance-layers-and-their-gates) defers natural victory/balance to Layer C, while DEV-0.7.2.12 has demonstrated that essential UI feedback is a **Layer A** blocker. The old gating text is historical sequencing, not a reason to hide or fabricate results.

The next independently authorized **Gameplay UI Migration Priority And First-Slice Decision** should:

1. Re-read this index, the latest DEV-0.7.2 parent/repair outcome, and the live `InGameShell`, `AppLayout`, `TopStatusBar`, `WorldPanel`, `uiViewModel` and session/owner paths.
2. Decide explicitly whether **prototype/implementation of UI architecture** may move ahead of any separate Game-version promotion; do not conflate an implemented UI slice with Home activation, finished gameplay, or Game-version acceptance.
3. Choose a **single bounded first consumer**: a read-only encounter/combat workspace view-model with truthful action phases/results, or a non-authoritative shell prototype using already supported domains. Avoid rebuilding the entire shell and combat engine simultaneously.
4. Verify keyboard/focus, responsive typography, selected source/target/cost/phase/result parity and unknown/hidden-information policies. Keep exact command identity, selected snapshot admission, replay, save/load, and UI-versus-owner state boundaries unchanged.
5. Prove the pattern through real owner/caller and selected UI behavior before abstracting shared components and migrating World/Home, then Character/Activity/Quests/Codex/Chronicle one domain at a time.

**Do not** create a seventh domain card, a nested universal action menu, speculative enemy HP/damage, a UI-owned resource formula or new execution verbs because a concept image contains a button. Visual mockups and prototypes are non-authoritative until a named owner-approved implementation slice accepts them.
