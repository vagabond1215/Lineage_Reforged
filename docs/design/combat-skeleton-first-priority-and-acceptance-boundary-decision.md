# Combat Skeleton First: Priority And Acceptance Boundary

Date: 2026-10-20. Repository: `vagabond1215/Lineage_Reforged`. Owner-directed unversioned design/sequence correction after the independent selected combat-choice run at `e26f5a11`. **COMBAT_SKELETON_FIRST; BALANCE_AND_NATURAL_VICTORY_PROOF_DEFERRED_FOR_IMPLEMENTATION_SEQUENCING.** This is not a combat runtime change, milestone acceptance, Game-version decision, repeal of Game-version policy, or claim that all combat capabilities already work.

## Decision and rationale

The current creator, attribute distribution, starting bundles, skills, equipment, consumables, abilities, magic and future character development are subject to substantial change. A fresh Stonevein Warrior's success against one particular three-foe patrol is therefore **not** an appropriate prerequisite for completing the reusable combat engine and command skeleton. The two authentic selected defeats are retained as factual playtests; they do not prove unwinnability, broken combat balance, or a need for lower enemy damage. The most recent independent selected run **did** prove that a real ordinary campaign can explore, admit an encounter, offer independent basic and Arming Sword commands, accept each, spend the advertised resource, defeat an enemy, and resolve Normal-Stakes defeat/recovery.

Prioritize correct, extensible ownership and execution of actions over numerical tuning. Do not adjust encounter composition, HP, damage, accuracy, character allocations, starting gear or spawn odds to manufacture a victory. Do not force a natural victory merely to close this implementation lane. Stabilize mechanics and then integrate future creator/progression changes before the dedicated balance and representative-playability gate.

## What a functional skeleton means

The skeleton is **not** a universal finished combat game. It is a coherent engine-owned path in which current and future character capabilities can be injected as owner-validated actions without rewriting core encounter state, turn/tick flow, targeting, resource accounting, effect application, results or persistence.

For every **supported** action family, establish or explicitly identify the absence of:

1. **Concrete identity and provenance.** Exact action ID, equipped-item/spell/ability/skill source and owner; never let shared family tags silently replace a distinct command. Support creation inputs and subsequent gear/skill changes without fixed Warrior numbers.
2. **Legal projection.** Available, blocked-with-owner-reason, or omitted action/target options generated by an authoritative combat/domain owner. Enemy, ally, self and other permitted target dispositions need distinct checks; UI availability is not authority.
3. **Timing and resources.** Queue/replace/interrupt and action lifecycle, initiative or beat progression, execution/recovery, HP/MP/Stamina/other valid costs, cooldowns, preparation/ammunition/charges when owned, and rejection for stale, duplicate, invalid or unaffordable commands.
4. **Typed effect resolution.** Actual damage, mitigation, block, status, healing, support, control and item effects only where their owner exists; distinct applied result, cancellation and fail-closed unsupported hooks. The engine cannot invent a universal item/magic effect interpreter.
5. **Encounter lifecycle.** Authentic admission, player and AI turns, actor/target state, ally/enemy victory, Normal-Stakes defeat, cleanup and return to continued play. Both terminal branches can be verified deterministically in owner/integration fixtures independently of current encounter difficulty.
6. **Durability and disclosure.** Owner/result ledger and Chronicle integration where defined, Save/load/restart invariants for committed encounters/results, and enough player-facing feedback to understand action, target, cost, result and why an option is unavailable. Opaque selected damage/foe state should be recorded as a presentation gap, not guessed.
7. **Composable contextual presentation.** World/Combat UI and the accepted contextual command architecture consume the same concrete commands and owner revalidation. No parallel nested combat-command menu, UI-authored legality or global arbitrary action registry.

Each item above is a *review/acceptance dimension*, not a claim that the current repo implements it or authorization to implement every system in one slice.

## Acceptance layers and their gates

**Layer A: foundation/skeleton (next engineering priority).** Exact commands and targets; honest owner-supplied legality, resource/timing/effects; player/AI turns; deterministic success and defeat terminal paths; transactional boundaries and serialization; capability-specific negative tests. Valid proof: focused owner and real caller tests plus selected UI checks for actually exposed action families. Synthetic/controlled fixtures can demonstrate victory *mechanics* but must be labeled and never promoted as an authentic naturally selected victory.

**Layer B: cross-system integration.** Connect evolving creator, character stats, combat skills, equipment, ranged ammo and constraints, shield choices, spell ownership, abilities, consumables, conditions and contextual UI in separately owned implementation slices. Do not claim that unfinished magic/item systems have functional combat activation just because they carry metadata. Their contracts must be decided before code paths execute.

**Layer C: tactical balance and release/representative playability (deferred).** After the input systems and core mechanics stabilize, measure encounter composition, difficulty, winning strategy, progression and build variety with ordinary selected runs, including naturally achieved victory, meaningful choice, continued play and durable Save/load/restart. No present balance estimate is authoritative for future character creation. The old fixed selected victory matrix remains historical evidence and a valid *later* representative or Game-version proof target, not the immediate combat skeleton blocking gate.
