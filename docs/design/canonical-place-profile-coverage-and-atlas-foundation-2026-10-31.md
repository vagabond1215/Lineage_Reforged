## 1. Decision foundation: one canonical place, typed authorities, derived views

**DECIDED FOR THIS PREIMPLEMENTATION FOUNDATION (not executable activation):**

1. **Do not create `locations.json`, `world.pois`, a new SQL location master or a separate editable map-marker database.** Present authored place identity stays in its specific canonical world files. Atlas and Current Area consume typed `(placeType, canonicalId)` references and derive live descriptions from that exact owner. `packages/db/migrations/001_world.sql` does not provide a universal `locations` table.
2. **Existing place/profile enrichment precedes mass new location generation.** Edit a region in `regions.json`; a locality in `region_localities.json`; a settlement in `settlements.json`; a district or site in its own registry; a semantic landform in `map_features.json`. A later developer authoring interface will edit those existing owners through validation, review and provenance, not a second copy. Procedurally generated *world-instance* places, if approved under PR #46 world-first, will require a separate seed/instance identity decision rather than rewriting base canon.
3. **Canonical ID is not display name, map pixel, runtime destination key or narrative alias.** Rename using owner-sanctioned `name/aliases` without changing existing stable IDs. A region and semantic physical feature can legitimately share a display name, while their typed IDs remain distinct.
4. **Profile visibility is not place visibility.** Authored full profile, geographic knowledge tier, session `knownLocations` state, runtime/current observation, source disclosure and map background disclosure are different inputs. A source-authored `summary` cannot reveal secret facts merely because the UI can fetch it; no reader automatically gains full profile access from geographic proximity.
5. **Parent/context anchor is not an exact map pin.** Only verified owner-associated reference coordinates or feature geometry can generate a map marker. Districts, sites and religion-owned places without their own registered point/outline are nested *list/profile* entries until a distinct exact geometry owner exists. `visualMapRef` on a settlement is optional and visual-only, not a travel permission or route.
6. **Optional emptiness does not license fictional enrichment.** No autogenerated aliases, race mixes, NPC biographies, geology, work/production effects, sovereign claims, quests, services or leyline nodes. Empty `aliases`, absent optional region demographic on subregions and null `parentDistrictId` can be correct. Candidate enrichment requires an existing concrete source and schema-valid, consumer-relevant field.
7. **Planned is not active.** A planned semantic named map feature may be retained in source and included in developer references, but must not become an implicitly discovered actionable place or an automatically exposed first-person landmark. Any visible named geography needs an explicit status/display and player-knowledge decision.
8. **Current-historical split:** frozen accepted logs/receipts retain historical snapshot wording and source; current Codex/Atlas display derives from the current canonical owner where identity and permitted disclosure resolve. Do not mutate the selected Save or current travel compatibility mappings while native-v3 Codex work runs.

These decisions implement existing `world-geography-authority-boundary-decision.md`, `settlement-identity-schema-decision.md`, `discovery-poi-boundary-decision.md`, and PR #45's single-source reconciliation. No separate canon approval is claimed.

## 3. Proposed read-only profile projection and authoring interface boundary

A reader-side *federated function* may take:

```text
resolveAtlasProfile({
  placeType,                  // discriminated canonical owner family
  canonicalId,               // exact source ID, never a search label
  viewerKnowledge,           // actual current player/session/discovery owner
  mapId,                     // explicit requested visual map
  sourceRevision             // repeatable content-version fingerprint
})
-> {
  identity: { placeType, canonicalId, parentRefs, sourceOwner, sourceRevision },
  presentation: { displayName, allowedAliases, allowedSummary, profileSections, certainty },
  cartography: { geometryKind: none | registered_point | verified_feature_geometry,
                 mapId, geometryProvenance, renderability },
  access: { listVisible, markerVisible, detailsVisible, explanation }
} | typed fail-closed resolution
```

This is an **illustrative future contract**, not a new schema nor code selection. The owner is authoritative for names/descriptions; the map registry is authoritative only for registered geometry; the player/world owners determine disclosure. Build user-facing `profileSections` from fields already permitted by the specific source schema and the reader's entitlement. Never copy editable `name/summary/coordinates` into a second canonical `atlas_locations` data file.

**Suggested first authoring workflow:**
1. Select an **existing canonical** record by typed ID and confirm existing schema owner. Edit owner-allowed name, aliases, summary and descriptive profiles via reviewed source change (later controlled developer tool).
2. Validate strict schema, slug/ID stability, unique/intentional naming, cross-family semantic anchors, parent status, regional coherence, visual refs (if any), known/hidden projection, and dependent Save/travel/quest callers. Reject unknown fields; a new profile field requires an explicit schema/owner decision first.
3. Emit a **derived, source-revision-bound** profile projection and optional geometry lookup. The editing interface should preview *which existing views change* and any missing exact map geometry. It must not create or relocate a travel destination or reveal map knowledge.
4. Historical accepted receipts remain frozen. Current Atlas text refreshes from the revised source if the character is authorized to know it. If a save contains stale `KnownLocationState.name/note/x/y` facts, prefer an owner-typed **read-through** adapter after separate selected Save/compatibility tests, never a silent destructive migration during the current gear work.

**No new profile values were authored in this audit.** This is infrastructure/contract preparation only.

## 5. Product decisions: defaults versus genuine questions

### Defaults adopted for continued connector-only planning (may be revised before implementation)

- **D1: first edit scope** = enrich **existing canonical records**, not authorize new towns/POIs, and initially use **reviewed repository content edits** rather than a new developer admin UI.
- **D2: no speculative filling** = existing summaries and optional missing alias/profile fields are not auto-repaired. Enrich only when a concrete selected UI or authored-canon need and supporting source justify it.
- **D3: priority is an acceptance pilot**, not an enormous bulk content batch. Start with a region, a named semantic feature, one settlement (after local full-file source verification), and one child district/site. Golden IDs above are fixtures, not a content-change approval.
- **D4: no automatic character grants.** Atlas never creates discovery, route access, Knowledge evidence, dungeon nodes or quest progress from a source record, overlay or name search.
- **D5: names stay owner-authored and typed.** Equal literal names across types are not merged; genuine duplicates need editor-backed identity proof and consumer migration.

### Important decisions deferred to a specific implementation gate

1. **Q1 / viewer map policy:** Is the entire First World biome/elevation background visible as out-of-character reference, or must in-character maps be revealed? If full imagery exposes undiscovered geography, what explicit labeling/opt-in or separate view is acceptable? **Must decide before shipping a full raster inside character Codex Atlas.**
2. **Q2 / authoring approval:** Who may publish a canonical rename/profile correction (developer-only file review, later admin tool, or world-owner created variant)? Is player-written naming a separate private note or a canonical alias? **Must decide before implementing editing.** Default: developer-reviewed file changes, player annotations separate.
3. **Q3 / multiple names:** Which aliases are public historical/translated/colloquial names, and which are character-learned or secret? **Must decide before expanding alias behavior.** Default: source-owned attested aliases only; viewer-specific disclosure separately checked.
4. **Q4 / generated world places:** Can world-seed generation introduce new committed locations within a particular world, and when do they become discoverable? Who owns merge/identity collision and cross-world namespace? **Must decide with PR #46 world-first persistence, not before the initial static pilot.**
5. **Q5 / profile sections:** Which author-owned populations/cultural/economic/religious/environmental facts are *public in-character*, known only through evidence, or out-of-character encyclopedia material? Default: fail-closed when entitlement unclear; don't leak continent race distributions into localities.
6. **Q6 / exact site map:** Should districts/sites acquire their own authored point/footprint and local map scale, or remain nested under settlements for the first Atlas map? Default: **nested only** until a complete geometry+validation+disclosure owner is approved.
7. **Q7 / migration:** When, if ever, replace `KnownLocationState` display copies and legacy `location.*` travel keys? Default: no migration now; future typed adapter first and dedicated selected Save/recovery/quest audit before any persistent cutover.

None of these questions blocks the **current documentation foundation** or the review of existing canonical record quality. Q1 blocks release of an undisclosed *background map* and Q2 blocks a mutable editor; the rest are just-in-time.
