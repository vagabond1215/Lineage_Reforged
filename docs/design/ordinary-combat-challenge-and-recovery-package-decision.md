## Exact candidate and ordinary caller trace

Use **Stonevein (`settlement.stonevein`, `region.auric_marches`, macroregion `region.kaelvar`) with a Warrior Bundle arming sword, buckler and leather armor** as the provisional creator/loadout scenario. Stonevein is authored as a city; creator selection can include it through `getWorldSettlementOptions`. `createNewGameSnapshot` records a known `type: settlement` location and `player.start.settlement.stonevein`, so the existing recovery predicate can recognize the start if those exact facts survive the accepted campaign path. This is a source-derived candidate, not a browser acceptance claim.

The provisional encounter is existing `spawn.kaelvar.frontier_tracks` -> `encounter.kaelvar.roadside_kobold_patrol` -> authored kobold scout and raider members. It is low difficulty and hostile. The profile is region-scoped to `region.kaelvar` and requires frontier habitat tags. Creator sets `worldState.activeRegions` to `region.auric_marches`, leaves `encounterContext` absent, and gives no frontier habitat. `buildDefaultEncounterContext` uses that active region and empty tags. Consequently this normal start cannot select that profile as written. A generic macroregion substitution, settlement encounter, or habitat assignment would invent context authority; the prerequisite must choose an exact ordinary activity/travel context and its validated geography/habitat source.

Ordinary UI actions in `apps/rpg-ui/src/game-shell/gameplayLoop.ts` advance the snapshot clock and player body/runtime directly. No UI caller invokes `runGameTick`; the sole non-test caller found is `apps/sim-runner/src/index.ts`. `runGameTick` would run world candidate resolution and pass `pendingSpawnCandidates` to `tickCombatFoundation`, which automatically takes the first candidate when no encounter is active. The present path does not distinguish pending, admitted, consumed, stale, duplicate, or rejected candidates as campaign mutations. `createEncounterFromSpawnCandidate` checks template existence but does not validate candidate provenance, context, or repeated admission. The retained world-spawn audit's admission concerns remain live.

## Combat, outcome, recovery, and equipment

Combat engine supports a player combatant, equipment-derived actions, manual command staging, AI, resource changes, and `allies_victorious` / `enemies_victorious`. A meaningful first loop could offer a sword attack, shield block or bash where valid, target selection, and pause/advance while the encounter runs. Current `queueManualCombatCommand` changes encounter state directly; unknown action types fall back to basic melee in existing tests. The prerequisite must specify legal action/target admission, stale and unavailable results, and the accepted campaign mutation boundary before UI controls are exposed.

On either result, `tickCombatFoundation` appends a capped 24-entry `combatHistory`, emits an event, clears party combatant bindings and removes the active encounter. It does not call `resolveNormalDefeat`, publish a campaign mutation, or project a durable success consequence. HP zero is synced to the player before the encounter is cleared. Success may truthfully end with the existing bounded history/event and no loot, wallet, quest, reputation, or other invented reward, subject to accepted campaign publication and restart proof. Skill-gain attempts already exist, but their durable application also needs the accepted transition.

`resolveNormalDefeat` itself is nonterminal and clears encounter/UI state, restores positive HP and usable Stamina, preserves MP, applies four recovery ticks when a destination is verified, and writes one receipt/ledger/Chronicle/notification set. It checks explicit or current settlement, then campaign-start settlement; malformed present authority yields `recovery_pending` rather than choosing another location. Recovery completion and duplicate validation have focused persistence tests. For the proposed Stonevein start, the creator's known settlement row is `type: settlement`, unlike a harbor row; that establishes a plausible safe destination under the current exact predicate, not an end-to-end combat recovery proof. The prerequisite must bind the admitted encounter's HP-zero result to one accepted source mutation, carry the verified Stonevein or other exact destination, block ordinary actions while pending, and cover publication failure, save/reload, duplicate, stale, conflict, and recovery completion. Starfall Port is not accepted as safe by harbor status.

The Warrior Bundle includes the chosen arming sword, buckler, and light armor. Creator equips them and live combat item profiles map the sword/shield/selected armor. This candidate needs no general item-instance or starter-equipment repair. Hunter short bow and butcher knife gaps are outside this route.

## Minimum text-first presentation contract to decide with the prerequisite

Show a context and encounter label only after accepted admission; roster names only for observed actors; player HP/MP/Stamina, relevant accepted statuses, current target, legal action labels/costs, action timing or pause state, and a concise resolved outcome. Present enemy resources or intentions only if an explicit observer rule permits them; never expose spawn rolls, hidden tactics, weakness scores, or undiscovered geography. Controls need keyboard/focus order, readable narrow/wide layout, disabled or explained unavailable/stale actions, and distinct no-encounter, forming, active, paused, resolved, recovery-pending, and playable-recovery states. The existing read-only presentation audit found source fields but no observer/label authority; this paragraph is an acceptance requirement for the prerequisite, not approval of a UI implementation.

## Persistence and capacity gate

An active encounter is serializable and combat history is capped at 24, but a real repeated loop can add skill state and, on defeats, unbounded defeat receipts, authority-ledger rows, Chronicle and notifications. The retained Soundings probe peaked at **5,076,206 / 5,242,880 UTF-16 bytes**, leaving **166,674 bytes**. This proposed repeatable loop consumes the existing additional-durable-history storage reopening trigger. Before implementation, measure a bounded sequence with success, defeats, save/reload and publication retries on the actual campaign path; decide retention and quota-failure behavior without deleting accepted witness/history. No new capacity claim is made from the present unit tests.

## Prerequisite exit and later acceptance plan

The single prerequisite decision must identify: one ordinary player action and exact geography/habitat source; candidate identity, eligibility, ordering, consumption, expiry and duplicate policy; accepted encounter start/commands/outcome mutation and save/publication owners; Normal-Stakes destination and `recovery_pending` completion; conservative observer/label/control contract; and the bounded storage measurement gate. It must name precise files, tests, and no-reward exclusions for a subsequent implementation package. If a product choice about where the encounter occurs cannot be derived from accepted world authority, record that exact question instead of fabricating canon.

Subsequent implementation acceptance must start from creator-selected Stonevein and the selected ordinary action, without fixture injection; show an authored encounter with legal manual choice; prove success cleanup and truthful no-reward result; independently force a normal defeat through the same caller and verify one receipt, safe destination, continued play, save/reload, duplicate, pending/repair, stale/retry and publication failures. Include focused world/combat/campaign tests, real UI render/accessibility checks, storage growth, content lint, app build, TypeScript/JavaScript mirror parity, and the known broad UI diagnostic baseline. These are future gates, not checks claimed by this decision.

Exclusions: generalized spawn/ecology, simultaneous encounters, gambits, party/NPC runtime, loot/economy/reputation/quest rewards, inventory instances, injury/trauma, broad combat redesign, and game-version or milestone advancement. No existing campaign/save was changed.
