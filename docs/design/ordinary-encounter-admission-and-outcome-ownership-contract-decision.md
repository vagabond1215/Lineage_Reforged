## Result and product direction

**CONTRACT_ACCEPTED; IMPLEMENTATION_HELD.** This is a reusable encounter-admission and outcome owner contract, not a canonical first-encounter script. The user explicitly directed that the first encounter vary with authoritative starting city/location and ordinary player actions. Stonevein and its caravan/frontier approach are one reference case only. No universal Stonevein, Kaelvar, kobold, or fixed first-encounter rule is accepted. If authored world data cannot derive eligible geography/habitat for the accepted action, the result is `no_eligible_encounter` or an unavailable action; no region, habitat, hazard, candidate or foe is fabricated.

The contract is decision-complete as a fail-closed owner boundary. A positive ordinary playable encounter and its implementation package remain **held** because no current player-facing action supplies the required authored encounter context, the existing Stonevein world records do not authorize one of the spawn profile's habitat tags, and the repeatable-history capacity gate has not been measured on an actual campaign caller. The next route is a separate **Ordinary Encounter Context Authorship Decision**, documentation only. It must select one exact action-to-place/habitat mapping and a reachable positive reference case before any combat implementation is packaged. A bounded storage measurement remains an implementation preflight after that positive route exists.

The hex/edge give geography and risk descriptors, but neither gives `frontier_track`, `roadside_ditch`, or `quarry_edge` habitat authority. A place name, `frontier_entry` mode, `ore_ridge` terrain, pass edge, `wildlife_risk`, or prose is not an accepted conversion to those tags.

The existing `spawn.kaelvar.frontier_tracks` profile and `encounter.kaelvar.roadside_kobold_patrol` template are possible authored references, not a guaranteed result. The profile's macroregion, habitat, hazard and weighted templates must all be respected. Current creator world state has no `encounterContext`; the ordinary travel/activity paths advance their own clock and do not call `runGameTick`. `runGameTick` is reached by the simulation runner, not the UI. `tickCombatFoundation` takes the first pending candidate without a durable admission transition; its manual command path can fall back from an unknown action to basic melee. Its resolved outcome clears the encounter and records capped history but does not itself enter the accepted campaign mutation/Normal-Stakes recovery path.

## Reusable admission contract

1. A player-facing action's existing owner first accepts an ordinary command against the exact source snapshot and campaign control. The action supplies stable command/result identity, actor, tick, location or route segment, and an **explicit authored encounter-eligibility link**. Merely advancing time, arriving in a city, or choosing a starter city does not start combat. A declined, stale, incomplete, or `recovery_pending` action cannot generate a candidate.
2. The context resolver verifies one unambiguous current place: player location and known-location record agree; a selected world hex or edge is explicitly linked to that place/action; local region matches the hex and has a valid authored parent chain. A profile may target that local region or an accepted ancestor macroregion, but the candidate retains the exact local place and source action. Missing, multiple/conflicting, or stale place links return unavailable rather than choosing a first array element.
3. Habitat tags come only from an authored action/place eligibility link and must intersect the profile and template tags. Terrain, barrier, hazard, spawn mode and prose are separate vocabularies and cannot be converted by string resemblance. Hazard pressure comes from an exact authored context value or an explicitly chosen applicable region profile with recorded provenance; no silent default `35` for an ordinary campaign admission. Candidate generation checks profile place anchors, region hierarchy, habitat, hazard interval, movement/disposition and template/member references before applying stable rate/weight selection.
4. Seed and ordering are bound to accepted campaign/action identity and a versioned selection rule. Sort eligible profiles/templates by stable ID before draws; retain selection input/version or a compact equivalent receipt. A candidate occurrence identity includes campaign/continuity, accepted action, exact place and selection ordinal, with profile/template IDs linked in evidence. Tick plus template ID alone is insufficient across actions, reloads and campaigns. No eligible candidate is a successful no-encounter action result, with no combat or defeat effect.
5. One accepted campaign mutation atomically links the action result, selected candidate, admission receipt and newly active encounter. Validate candidate still pending and source-identical; reject stale, duplicate, conflicting, malformed and already-active submissions before mutating. Consume or explicitly expire the candidate in the same transition. One active encounter is the first-package limit. The durable receipt must allow a post-restart duplicate to return the accepted result without another encounter or reward; a conflicting same identity fails closed. Current `pendingSpawnCandidates` and capped `combatHistory` are insufficient as sole durable duplicate evidence.
6. Legal player commands are derived from the active player's actual granted actions, current resources, target disposition/alive state, timing and control posture. Bind each command to encounter ID, actor, target, source revision and stable command ID. Reject unknown, ungranted, stale, wrong-actor, wrong-target, resolved/paused/pending and unaffordable input before queue replacement or other mutation; the existing unknown-action melee fallback must not be exposed through the campaign caller. Engine timing, AI and resolution remain authoritative; UI owns neither a clock nor combat formulas.

## Resolution and Normal-Stakes recovery

An accepted outcome mutation links the exact admitted encounter and last accepted combat state. On `allies_victorious`, clear transient combat/party bindings, retain a compact source-linked result/history fact, show a truthful outcome, and continue ordinary play. No loot, wallet, reputation, quest credit, item, or guaranteed skill progression is implied; existing skill-gain rules may apply only through accepted state and their own caps.

On player HP zero / `enemies_victorious`, the accepted proposed snapshot reaches campaign-session admission with HP zero, complete encounter cleanup and the same source mutation identity. `admitCampaignMutation` already invokes `resolveNormalDefeat` for an accepted HP-zero proposal; this owner must issue exactly one receipt, ledger entry, Chronicle and notice set. It must preserve nonterminal Normal Stakes, clear combat UI, restore positive HP/usable Stamina and preserve MP. A failure before campaign admission leaves the source snapshot unchanged. Duplicate after caller-state loss or restart returns the accepted result; conflicting duplicate or partial retained evidence fails closed. Non-head continuity forks, publication readback/retry, save/load and repair completion must preserve the exact encounter-to-defeat link.

Recovery destination is verified by `normal-defeat.ts` against one known `type: settlement` row with matching settlement ID. An explicit destination needs the same validation. Otherwise current settlement is tried, then campaign start; a malformed present source produces `recovery_pending`, not an opportunistic fallback. Stonevein creator source has a known settlement row and start flag and is a plausible reference. A context away from a settlement must accurately represent current location and may use the verified campaign-start settlement; the action/encounter area is shown separately from the last committed travel location. Starfall Port or any harbor is never safe by harbor label alone. While pending, ordinary encounter/travel/activity commands stay blocked; the existing recovery-repair owner validates one destination and durable completion before play resumes.

## Minimum presentation and persistence gates

Present an encounter only after accepted admission. Display the accepted action/place label, encounter state/tick, the player's exact HP/MP/Stamina and accepted statuses, allied and targetable foe tokens, legal action labels/costs, target and queue state, a short log, and accepted success/defeat/recovery result. In the absence of an observer/recognition owner, use stable generic foe labels (`Foe 1`, `Foe 2`) and do not show enemy exact resources, names, tactics, hidden identity, rolls, weakness or future action. A later accepted observation rule may allow more. Distinguish no eligible encounter, no active encounter, active, paused, stale/unavailable, resolved, and `recovery_pending`; explain disabled controls. Provide keyboard focus/order, readable narrow/wide text, accessible status changes and log review without auto-moving focus. This is a bounded contract, not a broad combat screen or gambit system.

Active encounters can serialize and `combatHistory` is capped at 24. Admission/outcome/defeat receipts, campaign control, Chronicle and notices may still grow with repeated challenges. Retained Soundings evidence reached 5,076,206 / 5,242,880 UTF-16 bytes, leaving 166,674 bytes. Before a positive implementation package, measure the actual creator/action/admission/command/success/defeat/save/restart/publication path under an instrumented 5 MiB storage limit, including every temporary write, a repeated bounded campaign sequence and failure/retry. Decide bounded receipt retention and quota-failure posture without deleting accepted witness/history or claiming unlimited play. No current-path measurement can substitute for this because the positive caller/context is absent.

## Implementation hold and future acceptance

The next documentation decision must author **one** action-to-world-hex/edge/habitat link in existing world/action authority and prove a reachable example from creator and accepted action, while keeping the resolver reusable for other origins/actions. It may select Stonevein's approach only if the exact place and habitat are actually authored. It must not modify unrelated starts, invent a universal first encounter, or turn no match into a fight. After that, the bounded storage gate must pass before an implementation prompt is installed.

Future implementation acceptance requires both a positive and negative creator-to-action path without fixture injection: matching source admits exactly one authored candidate/encounter; nonmatching context remains `no_eligible_encounter`; legal manual choice changes state; unknown/stale commands fail closed; success cleans up and resumes play with no fabricated reward; defeat creates exactly one Normal-Stakes receipt, verified destination or reachable pending repair, then resumes; save/reload, duplicate, conflict, publication failure and quota failure preserve authority. Test local/macro region, place/habitat, seed/order, restart, reversed/duplicated receipts, and TS/JS mirror parity; run content lint, app build, browser text/focus/readability checks, and compare broad UI diagnostics with the known 137 baseline. This decision claims no such implementation or acceptance.

Exclusions: automatic city-arrival hostility, generalized ecology or world tick activation, simultaneous encounters, gambits, NPC party, loot/economy/reputation rewards, item instances, injury/trauma, broad UI redesign, game-version or milestone advancement.
