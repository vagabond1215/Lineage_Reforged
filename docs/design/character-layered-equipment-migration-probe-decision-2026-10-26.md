# Character layered equipment: historical migration probe checkpoint

Date: 2026-10-26
Status: `READ_ONLY_PROBE_VERIFIED; LIVE_MIGRATION_HELD`
Source: fetched `master` `cf8eb7a8d1e4a3acf389b5f02ed036047fc58737`; draft PR #17 follow-up audit at `9f427961ebcc2945522aa09e6a4b8985dfd01e65` is design evidence only. Game `0.1.1-prealpha` and the parked DEV-0.7.2.13 route are unchanged.

## Decision and implemented boundary

The first owner checkpoint is a **pure, versioned migration probe** in `equipment-migration-plan.ts`. It reads an existing 17-key `SaveSnapshot`, keeps an independent copy of the complete source equipment map, and proposes deterministic per-unit IDs and left-first positions. It never writes the snapshot, equips an item, changes the clock, changes a save version, or registers the proposed IDs as live instance authority. The current Overview, equipment actions, resource/combat readers, save admission and historical survey witnesses remain on the old owner shape. A `candidate` plan means only that this structural inspection found no blocker; it is **not** item-fit, ownership, migration or activation approval. Every plan carries `activation: not_authorized`.

The source map must contain precisely the historical 17 keys. A malformed ref or impossible quantity blocks the plan. For unsided Ear/Eyes, the first unit is proposed for left Ear/Eye; any additional unit remains recorded as unplaced, not silently shifted to the right. Fingers units can be proposed for L. Ring 1 and L. Ring 2 in stable order; excess remains unplaced. The complete original ref, including quantity, durability and modifiers, remains in `sourceEquipment`. A legacy ref with quantity greater than one and a single durability or modifier value is blocked because one scalar is not valid per-instance provenance. The bounded preview prevents a corrupt count from allocating an unbounded unit array. No item art, name heuristic or slot eligibility is inferred.

This probe intentionally **does not** create durable non-fungible identity. Proposed IDs are deterministic for the inspected snapshot and may change with a later capture tick. They cannot be used as stable ownership references. It also does not activate Back, right Ear/Eye, the ten real Ring positions, clothing layers, saved presets, or the one-watch Equip action. The complete requested feature remains held.

## Contract required for the next owner slice

1. Introduce one versioned live item-location owner before conversion: each physical wearable has one durable ID and one location (worn position, bag, overflow or another established location). Existing fungible stacks need an explicit, lossless decomposition or a retained ambiguous-source envelope. Current UI session flags and stack merging cannot carry per-instance durability or identity. Unknown per-unit metadata must block conversion or be preserved in a recoverable source record; never copy one durability to several items or erase a remainder.
2. Make conversion idempotent with a persisted source-version/receipt marker and stable instance IDs independent of save tick. Convert only current live player equipment, inventory and overflow. Historical Ashen Reef `ownerInputs.equipment` and fingerprints retain their exact 17-key serialized meaning; new survey capture must project effective worn state to that historical witness contract or use an explicitly versioned new witness. SaveManager's `0.6.0` admission/readback needs a separately validated compatibility path. Repeated load/save/restart must neither duplicate units nor reassign identity.
3. Treat Equipment, Casual/Clothing and Accessories as views/plans, never separate physical inventories. Clothing can remain worn beneath compatible armor. Combat and Casual accessory presets can both reference the same owned ID, but only one physical location exists and only effective worn equipment drives combat hooks, resource modifiers and progression readers. A sold, destroyed, displaced or stale preset reference is unavailable, not an item source.
4. Author actual layer, coverage, sided fit and Back/ring eligibility in a dedicated item/profile contract. The current broad resolver and item-name heuristics are insufficient. Unknown fit fails closed. The final position schema must cover Back, L/R Ear, L/R Eye and L/R Ring 1–5 as real saved positions without rewriting old witnesses.
5. Define one atomic apply command. Before mutation it validates the whole target, current revision/request identity, owned instance locations, occupied slots/displacements, storage capacity, fit, active combat and genuinely modeled inability/ability authority. No-op and stale/blocked requests cause no clock/body/world/resource/inventory effect. One accepted configuration change records one receipt and advances one watch (six ticks) through the complete time owner exactly once; replay returns that receipt. The timing of effects during the watch and interruption behavior need explicit owner rules. Merely viewing a category or preset costs no time.

## Verification and limits

Red-before-green tests cover single legacy left mapping, multiple units with shared durability and overflow conservation, malformed quantity, deterministic repeat/serialization, and unchanged `SaveSnapshot`, resource/equipment and Ashen Reef validation. Existing combat/equipment/resource/Save tests and the UI suite remain regression guards. These checks prove that the **probe** does not disturb live state; they do not prove a converted live save, an equip/unequip cycle after conversion, selected gameplay, Save/restart of new identity, or timed loadout application. Those remain acceptance gates for subsequent owner slices.

No branch or PR is merged or retired by this checkpoint. PR #17 stays a draft design reference; PRs #5–#16 retain their named evidence/selected-acceptance holds. The next exact review trigger is a durable instance/location owner proposal with a versioned old-save conversion and historical-survey projection test.
