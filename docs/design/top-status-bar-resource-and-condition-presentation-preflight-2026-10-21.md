## 3. Exact independent UI surface

1. **Readable primary resources:** HP (red), MP (blue), Stamina (green) as three meaningful, **capsule-free** horizontal bars with truthful `current / max`, accessible names and visually bounded fills. Use current theme tokens, not hardcoded math or replacement colors. Do not reinterpret percentages as stamina regeneration or as metabolism. Keep values correct for zero or invalid maxima, warnings and combat updates. Fixed readable widths preferred; at constrained widths use a well-labeled wrap/reflow/scroll layout, never silent clipping or fake truncated values.
2. **Meaningful conditions only:** hide the **permanent neutral `Condition: Stable` capsule** when all owner-projected states are normal. When conditions are warning/critical, show a compact focusable status affordance keyed by actual state and severity; trigger opens typed label, severity, tooltip/cause, trend and existing appropriate actions/details. Ensure hydration and severe deficits are not suppressed by an unrelated stamina warning. Do not infer buff type, duration or recovery suggestion that the owner does not provide.
3. **Preserve shell utilities:** identity, calendar/climate popup, bell notifications, settings + embedded save/quick-save/retire/menu controls, meaningful body toast/notice, global six-domain rail, active panel and focus return. No unowned "Home" button, altered game clock or newly simulated weather.
4. **Responsive/accessibility:** focus-visible, expanded-state and controlled overlays, Escape/dismiss/return path as appropriate to the current overlay contract, reduced motion, readable text at common zoom and phone/narrow-window layout. Avoid clipping a condition popover inside an overflow-x container; overlay layering must work when resource bars wrap.
5. **Honest nutrition deferral:** hydration can use the existing `hydrationLevel` and owner band. Current `energyBalance` is daily rollover coverage, not signed continuous calorie balance. `energyReserve.quick/stored` and `dailyCarbs/Fat/ProteinConsumed` are not positive available nutrient reserves. **Do not render Energy surplus/deficit or Carbs/Fat/Protein composite bars** until accepted owner/storage contracts exist. This slice is explicitly not nutrition implementation.
6. **Scoped code footprint:** prefer `TopStatusBar.tsx` and an isolated resource-meter/status subcomponent or small presentation helper; a bounded type/projection adapter only if required. Do not modify `CharacterPanel.tsx`, `WorldPanel.tsx`, `GameSessionContext`, item commands, combat owners, shared save/state contracts, nutrition, global nav or launcher. Preserve current view-model fields and API callers. If genuinely necessary, use an owner-backed projection at the `TopStatusBar` boundary without introducing a new unvalidated gameplay layer.
