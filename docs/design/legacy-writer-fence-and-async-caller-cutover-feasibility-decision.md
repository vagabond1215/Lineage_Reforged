## Decision

**SAME_ORIGIN_OLD_WRITER_EXCLUSION_UNPROVEN; CLEAN_EPOCH_ALLOWED_IN_PRINCIPLE; ACTIVATION_HELD.** No browser or deployment evidence establishes that all older JavaScript contexts on the existing origin have stopped writing legacy `localStorage`. The current save, profile, attempt, launcher and lifecycle owners make synchronous writes without an epoch/fence check. A newly deployed check, IndexedDB marker, `navigator.locks` request, `BroadcastChannel` message, storage event, refresh request or localStorage sentinel only governs cooperating code; it cannot alter an already-running older writer. A stable source census is a snapshot, not a future-write exclusion. Do not activate a new IndexedDB authority, assert that old writers have stopped, delete old keys, or accept capacity/combat/parent completion from this evidence.

The owner's waiver removes the need to materialize, reconcile, export/import or preserve pre-cutover legacy saves solely for backward compatibility. Slice E/F records remain inert evidence and historical checkpoints, not the mandatory source of a clean-epoch campaign. A clean epoch still needs a deployment/version boundary that keeps old clients from corrupting or superseding **new** authority, including its account access. Async repository and caller-state preparation is technically possible behind a disabled new-epoch gate, but the earlier full Slice G contract includes a demonstrated fence and reset/delete safety. It is **not admitted as one implementation package** from this evidence. No production source, deployment, site access, user browser data or storage changed in this decision.

The active Sites preview is owner-only, but one owner may have multiple tabs, browser profiles or devices. A server asset update affects later requests; it does not revoke an already loaded script's access to its origin storage. No current mechanism provides a no-unacknowledged-writer proof. Browser eviction, closing a tab, or a user refresh may change individual state, but the repository cannot observe that as a durable all-client barrier. A two-stage same-origin deployment can first make *new* clients fence-aware and later allow selection for only those cooperating clients; it still cannot prove that pre-fence clients are gone. That protocol is a candidate, **not accepted** here.

IndexedDB and `localStorage` also have no shared browser transaction. A new client can check an IDB fence before a legacy write, but an old client can write between the check and the localStorage operation or immediately after selection. A close/reopen readback or second census detects some races but cannot rule out that later write. Head/epoch compare-and-swap is meaningful for IDB-selected writes inside one IDB transaction; it is not a cross-API lock on old code.

## Smallest safe G boundary after the origin decision

The conversion must cover one async account repository and every caller that can read, repair or write account/campaign authority; an IndexedDB-only helper would leave the live app on the old path. The repository needs explicit `loading`, `pending`, `blocked/repair`, `stale`, and `unavailable/quota` results. Sign-in and app bootstrap must await exact profile/slot/selection readback; storage failure must never produce an empty playable account. Every write must recheck account epoch/head and selected authority in the appropriate transaction, with no fallback to legacy writes for an IDB-selected account. Advisory cross-tab signals may prompt refresh but do not establish authority.

## Same-origin clean epoch and stop condition

The owner selected the **existing origin** and waived pre-cutover save compatibility. A candidate clean epoch would use a new, versioned IndexedDB authority that no older client can name, plus versioned account/session/credential/active-pointer ownership or a password-verified rekey. New code must never read or fall back to old save/profile/attempt keys for a new-epoch account, and old reset/delete enumeration must not reach new data. The v3 canonical copy is not selected. Pre-cutover keys may remain obsolete until a separately proved cleanup; leaving them is safer than deleting them during an unproven old-tab race. This is a design candidate, **not an accepted fence**: the published old bundle must be inspected or otherwise bounded to prove it cannot open/delete the new database, clear all origin storage or alter the new auth namespace. New code must prove no fallback, cross-account alias or shared key path. Account identity, credential transition and user-facing start-new-campaign wording remain specific decisions for the next route.

If the requirement is literal exclusion of all already-open old scripts from *any* same-origin legacy write, the current repository/Sites surface cannot demonstrate it. A browser does not expose a reliable all-tabs termination/acknowledgement barrier to this app; owner-only access does not change that. Activation then stays held until an external old-client-retirement proof exists. If the owner accepts **provable non-interference** instead, old tabs may continue to write only obsolete namespaces while the new epoch is isolated. That alternative needs exact old-bundle audit, a new namespace contract, real old/new tab tests and no legacy fallback before it can be accepted. Neither alternative is accepted in this decision.

New-epoch durability retains full non-head/fork campaign history, profile/Legacy state, independent Soundings provenance, restart/retry/repair, user-controlled backup/restore, dynamic quota and two-browser long-run workload gates. The waiver applies only to pre-cutover legacy data. No new site, origin, database or auth namespace is created here.
