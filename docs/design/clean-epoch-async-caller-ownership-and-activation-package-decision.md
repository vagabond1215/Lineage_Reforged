# Clean-Epoch Async Caller Ownership And Activation Package Decision

Date: 2026-09-30. Unversioned cross-owner decision at clean, fetched `master` `631477f168ef9f828e053a7384a0b5aa9c4fecc6`. Game `0.1.1-prealpha`, playability `INTEGRATED_LOOP`, accepted `DEV-0.7.0`; planned parent `DEV-0.7.1` remains held. **ASYNC_CALLER_ROUTE_SELECTED; LIVE_ACTIVATION_HELD.** This decision changes documentation only.

## Authority and current capability

The owner says this is a sole-user development deployment and all pre-cutover browser data is disposable. The accepted route is a fresh `lineage.campaigns.epoch1` IndexedDB epoch, epoch-specific session hint, deliberate closure of old tabs and a later one-time origin/profile reset. No legacy import, reconciliation, export, old-save recovery, archived-bundle archaeology or public-production continuity work is required. The reset does not waive durability of data created after activation. See `development-only-clean-persistence-epoch-route-decision.md`.

`cleanEpochAccountStore.ts:301-342,349-375,388-598,598-612` opens the separate v3 database and provides account list/read/selected-hint validation, registration, revisioned profile/credential updates, prepared account-slot attempts, first publication, recovery and atomic first-campaign consumer completion. `campaignIndexedDbStore.ts:23-40,216-254,254-363` owns four-store artifact/control/slot/witness publication and head readback. Its low-level descendant publish is **not** a complete account-scoped caller API: it does not pair ordinary descendant publication with a durable account consumer plan and its `read` requires a known campaign and slot. `cleanEpochAccountStore.ts:499-533` ties first recovery readback to the currently published slot/head, so descendants require a generalized recovery contract before they can be offered as playable epoch loads. Neither owner lists epoch slots, resolves an ordinary load by slot, reads retained non-head artifacts as a validated historical authority, durably closes/deletes an epoch slot/account, or provides post-epoch backup/restore. G4's 35/35 native browser QA, publication 12/12, adjacent tests 68/68, Node typecheck and Vite build are reused evidence, not fresh tests for this decision.

## Ordered implementation packages

1. **G5 — Inert clean-epoch slot inventory and verified first-head load.** Add account-scoped async `listSlots` and `loadSlot` (names are illustrative) behind `CleanEpochAccountStore`, with only narrowly needed support in `campaignIndexedDbStore.ts`; use existing save metadata/session-control types without calling localStorage. Verify account identity, complete first-campaign recovery, slot/head/control/artifact identity, closed/terminal posture and Soundings first witness. A descendant head must return an explicit blocked/unsupported result until G6 generalizes its recovery and consumer contract; it must not be mistaken for an empty or playable slot. A missing slot is distinct from malformed authority and IDB failure. Preserve exact bytes and read-only behavior. Native browser QA must cover multiple accounts/slots, empty versus corrupt, pending versus completed consumer recovery, closed head, restart, blocked/unavailable and injected read failure. No App, launcher, legacy owner or activation edits. This is the **installed first implementation slice**.
2. **G6 — Inert descendant publication, history and general consumer recovery.** Give the clean-epoch owner a guarded account-scoped descendant transaction using expected campaign head **and** expected account revision. Persist immutable accepted artifacts and validated parent/continuity identity, including permitted non-head/fork history, without pruning; retain first Soundings witness/artifact and full nested source history. Couple every required profile/Chronicle/Legacy consumer plan to accepted publication and exact retry/recovery. Test two tabs, stale head/account, same-source retry, lost caller, abort/quota and non-head reload/fork. A raw call to `CampaignIndexedDbStore.publish` must not become the App route.
3. **G7 — Epoch account/auth/session and first-campaign orchestration adapters.** Adapt `launcherAuthManager.ts`, `accountProfileManager.ts`, `newCampaignAttemptCoordinator.ts` or new focused modules to async epoch APIs. Preserve credential verification, revisioned account mutation, stable attempt identity and first-publication completion, with no old-key fallback. Keep old App selected until coordinated caller conversion; prove native browser registration/sign-in, restart, failed IDB, stale account revision and prepared/accepted-pending attempt recovery.
4. **G8 — Async App bootstrap, load and ordinary save actions.** Convert `App.tsx` bootstrap and signed-in navigation, slot listing/load, new campaign and ordinary manual/quick publication to awaited epoch adapters. Replace empty-slot/default-profile failure fallback with reachable blocked/retry UI. Prevent double action on pending writes; after rerender/restart resolve retained operation before offering a new identity. Verify ordinary UI paths, exact readback, Soundings, concurrent tabs and failure notices in native browser. Do not leave any real campaign caller selecting old storage while claiming activation.
5. **G9 — Lifecycle, account reset/delete and remaining account actions.** Convert retirement/defeat repair, blocked-run purge, profile/Legacy actions, slot closure/deletion, account reset/delete and sign-out. Define idempotent epoch transaction/recovery for destructive account transitions and session invalidation; preserve retained accepted history except on an explicit epoch account deletion/reset requested by the player. Test interruption at each boundary, replay, terminal settlement, estate/inheritance once, cross-account isolation and stale tab.
6. **G10 — Coordinated clean-epoch activation and durability acceptance.** Audit all production imports/storage writes and built output, verify every real campaign/account caller uses the epoch and no failure path falls back to legacy authority. Run ordinary native-browser create/save/load/restart/retry/recovery across two browser contexts and a long-running campaign with legitimate world, lineage, Chronicle, Soundings and non-head/fork history growth. Address dynamic quota/eviction and user-controlled epoch backup/restore before declaring post-epoch durability. Then, as a separate deliberate operational step, close all development tabs for each used origin/profile, deploy/relaunch the validated build, clear **only pre-cutover** development site data for that origin/profile before first new-epoch launch, and register fresh accounts/campaigns. Keep `127.0.0.1` and Sites origins separate; never clear an epoch after new data exists. An epoch-compatible build is required to read data after rollback.

Each package is conditional on its predecessor's exact readback and focused QA. Splitting a package is allowed at a tested inert checkpoint; moving activation earlier is not. Slice C's capacity/combat and parent `DEV-0.7.1` acceptance stay held. No Game version change follows from these packages.

## Stop conditions, evidence and branch disposition

An unavailable/blocked/quota/aborted/malformed database, missing first Soundings provenance, pending consumer completion, stale head/account revision, unverified non-head source or conflicting retry blocks success. Never silently generate a replacement identity, default account, empty playable slot list or success notice. Accepted post-epoch history may grow; the old 5 MiB localStorage witness is not a retention ceiling. Backup/restore, eviction and two-browser long-run evidence remain required even though pre-cutover test data is disposable.

This docs-only inspection ran no new browser QA, build or typecheck.
