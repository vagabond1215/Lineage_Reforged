## Candidate implementation

- `native-v3-staging/index.html` loads `src/nativeV3Staging.tsx`, which mounts the genuine `EpochApp` with its existing account registration/sign-in, native creator, gameplay and Clean Epoch persistence owners. It does not import disposable QA registration or take a query-string candidate switch.
- `EpochApp` retains its DEV-only QA entry for existing tests; the separate staging entry passes `stagingNativeV3`. The prop selects the existing native owner route; it is **not** an access control. The normal `main.tsx` and default `App` remain v2. The candidate review banner no longer claims a local-only session.
- `vite.native-staging.config.ts` requires `LINEAGE_NATIVE_STAGING_ORIGIN` to be one exact HTTPS origin different from the existing v2 preview. It emits only `dist-native-v3-staging/index.html` and assets, outside the normal `dist/client` and Sites build output. A bundle opened on another origin renders a blocking notice before `EpochApp` mounts. Local Vite preview accepts only an exact loopback origin with a port; production build never accepts HTTP. The origin check prevents accidental wrong-origin use but does not secure the host.
- No new account, Save, gear, survey, combat, lifecycle, schema or gameplay owner was added. Browser storage retains the existing Clean Epoch database name within its own origin; the separate staging origin supplies the data boundary. No existing browser origin is cleared or migrated.

## Rollback and acceptance

Before publishing, retain the previous staging revision (if any), the new artifact digest, project ID, access-policy evidence and a tested disable-access/revert procedure. On a failed staging check, disable access or revert only that staging project to its previous revision. Leave the deployed v2 Site and both origins' account records untouched. Do not use browser-storage deletion as rollback; preserve a user-held export before destructive account operations, which are outside this work order.
