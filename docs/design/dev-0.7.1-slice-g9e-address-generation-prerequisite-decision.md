# DEV-0.7.1 Slice G9E — Address Generation Prerequisite

Date: 2026-10-02. Source: synchronized `master` `4ebfc220df2b0948b303cd1cbb38c41a49cd044d`. Scope: clean epoch in `vagabond1215/Lineage_Reforged` only.

## Decision

**G9E_ADDRESS_GENERATION_CONTRACT_REQUIRED; DELETION_IMPLEMENTATION_HELD.** Hardened G9D is executable on this source. G9E cannot safely expose deletion using the v5 first-campaign slot keys. A deleted slot must become reusable while its first attempt, first recovery, immutable artifacts, Soundings witness and later recoveries remain retained. The existing attempt and first-recovery stores each have key `[accountId, slotId]`. `prepareAttempt` conflicts with a different retained attempt; `readRecovery` and `inspectSlot` require an address whenever completed first recovery exists. Removing only the address would make inventory fail closed, and deleting the attempt/recovery to make the slot reusable would violate G9A retention. Returning an empty slot without making a later creator attempt possible would misrepresent the ordinary selected-App control.

The smallest safe prerequisite is an additive **v6 slot-generation contract** before any player or terminal address deletion. This is a schema/owner repair within G9E, not a new gameplay feature or a new reward rule.

## Chosen contract for implementation

1. Add campaign-scoped first-attempt and first-recovery authority keyed by immutable `[accountId, campaignId]`, with the original slot ID and attempt ID retained in each row. Migrate verified v5 rows to v6 authority in the IndexedDB upgrade transaction; a malformed, duplicate or disagreeing row blocks upgrade. Keep immutable campaign artifacts, controls, descendants, terminal recoveries and witnesses. Do not delete old v5 rows until an independent retention decision; designate exactly one version as active read/write authority so the two copies cannot vote on truth.
2. Add one current slot-generation row keyed `[accountId, slotId]` with a stable `slotGenerationId`, campaign/attempt identity and `prepared`, `published` or `deleted` posture. `slotGenerationId` identifies one lifetime of one physical save slot and survives all publications within that occupancy. It is distinct from the existing save/publication `generationId` carried by `StoredSaveEnvelope` and newly minted with artifacts/publications. Never copy, alias, compare or derive one identity from the other. This row identifies a prepared campaign without an address and a deliberate deletion after publication. A fresh campaign may replace only a verified `deleted` pointer using the expected account revision and a newly minted `slotGenerationId`. Existing slot generations remain reachable by campaign identity. Never infer deletion from an absent `slots` row alone.
3. Add immutable address-deletion receipts keyed by account, slot and `slotGenerationId` plus deletion identity. Each receipt binds the exact old address artifact/publication/raw identity, campaign/character, pre/post account revision, reason (`player` or `terminal`), and timestamp. An exact retry reads the receipt and account/slot/control state; a changed request conflicts. Account profile revision, run-history membership, `slots` address removal, slot-generation posture and receipt commit in one transaction. On a nonterminal active run, the last address follows the accepted `markRunDeleted` active-to-deleted history/metric semantics. A retired or archived terminal run remains retained and is never marked deleted because its terminal history is still authoritative.
4. For terminal cleanup, require a completed G9D settlement and independent closed-head readback first. Remove all of that run's remaining exact addresses in one transaction, write per-address receipts plus a completion marker bound to the terminal recovery, and update run membership once. A retry checks the complete marker and every receipt. Terminal recovery must remain readable by campaign/publication even when its terminal slot address is gone; closed control, terminal/source artifacts, witness, settlement receipts and deleted-address receipts replace the former address-presence check. A missing address without matching deletion evidence remains corruption.
5. Permit a later campaign in a deleted slot only through a new `slotGenerationId` and account CAS. A stale tab using any old address or slot generation cannot publish, load or overwrite the replacement. Other addresses of the old campaign remain independent; its singular head and immutable history stay retained. First/descendant readback must resolve historical recoveries by campaign, not by a reused physical slot.
6. The selected G9D retirement path is an **archival terminal retirement** under the already accepted G9A terminal-settlement contract: it records `outcome: archived` with `archiveReason: retired`, resolves run payout/estate, closes campaign authority and does not create a lineage-inheritance source. This is intentional for the current selected path, not an accidental type mismatch. `retainRetiredRun(...)` is a separate retained-lineage transition that records `outcome: retired`; it is not selected by G9D or by the current selected-App terminal retirement caller. `resolveHeirSourceById` / `consumeRetiredRunInheritanceUse` therefore must continue to reject G9D archival retirement. G9E must not convert archival retirement into retained retirement, invent inheritance uses or fuse the two lifecycle meanings. Any future decision to make terminal retirement inheritable is a gameplay/lifecycle contract change outside this schema package.
7. Preserve existing first-campaign exactly-once inheritance consumption only for a genuinely retained eligible `outcome: retired` source. Test that retained-lineage source and the zero-use/ineligible archival-terminal outcomes separately. The selected creator currently supplies no eligible heir sources, so do not claim ordinary UI reachability or add an unverified selector in G9E.

## Acceptance before enabling deletion

- v5-to-v6 upgrade, restart and malformed/duplicate migration rejection; first campaign, descendant, Soundings, terminal and account suites stay green.
- Manual and quick deletion, one-address survival, last-address active-to-deleted history, terminal multi-address cleanup, restart/reuse of a deleted slot, and immutable historical recovery/witness retention.
- Prove repeated physical-slot reuse across at least three campaigns: campaign A in one slot -> delete -> campaign B in the same slot -> delete -> campaign C in the same slot. A and B historical attempts/recoveries/deletion receipts remain independently readable; their stale callers cannot mutate or load C; the current slot-generation pointer names only C; and no history, receipt, recovery or identity collides merely because the physical slot ID is reused.
- Assert the identity boundary directly in QA: each slot occupancy has one stable `slotGenerationId`, while save/publication `generationId` values may change independently across first/descendant/terminal publications and must never satisfy slot-generation CAS.
- Abort/quota at every transactional write, competing owners, stale account/address/slot-generation, cross-account request, changed retry, missing receipt, partial receipt, and lost post-commit readback. No failure becomes an empty slot or a duplicate inheritance consumption.
- Existing selected-App delete controls become available only after owner and real-caller proofs. G9F account reset/delete, G10, death callers, migration/cutover, Game-version and parent acceptance remain held.

No production schema, deletion control or browser user data was changed by this decision.
