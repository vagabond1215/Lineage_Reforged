## Decision

**MIGRATION_COPY_CONTRACT_ACCEPTED; ACTIVATION_HELD.** The smallest next implementation is an account-wide, non-activating, exact-raw copy and verification stage in version 2 of the existing `lineage.campaigns` IndexedDB database. Version 1's artifact/control/slot/witness publication transaction is a foundation for *new* publications, not a complete legacy importer: it cannot retain candidate, recovery, migration, attempt or account families, cannot represent every non-head slot, and has no active-authority marker. Do not replay old artifacts through `publish`, infer a history chain from its single predecessor, or treat `read` of one selected head slot as account completeness.

The copy stage retains **all** existing recognized campaign/account authority and matching unknown or malformed raw records without altering `localStorage`, current IndexedDB publication stores, or live callers. Its verified result is an inert source snapshot, not playable IndexedDB authority. A separate later package must materialize complete semantic records, make synchronous callers asynchronous, fence old writers, provide export/rollback, and activate one authority atomically after restart and exact readback. Merely copying bytes cannot clear the Slice C capacity failure or authorize combat, cleanup, or parent acceptance.

## Live source families and ownership

Capture original key and raw UTF-16 string exactly before any normalization or semantic projection. The present read paths can mutate: `loadSaveWithAuthority` may migrate v6, repair a legacy defeat or resume Soundings recovery; `loadAccountProfile` creates a default profile; launcher bootstrap can update session state. The copy stage must enumerate `localStorage` directly and use pure validation, never call those mutating readers.

The `save-slot` prefix is an obsolete detection family, not a new-format validator. Auth and preferences are inventoried for reset/quota/activation interactions but excluded from migration data. This is an origin-wide source census followed by account-scoped groups; a selected active account alone is insufficient.

## Non-activating copy and verification contract (next Slice E)

1. Upgrade `lineage.campaigns` from schema version 1 to 2 with additive **staged source records** keyed by `(copyId, originalKey)` and a **copy manifest** keyed by `copyId`. Keep the four v1 publication stores and their behavior intact. Staged records contain exact key/raw string, classified family/account when provable, raw byte-length/checksum, and validation posture; unknown/malformed records are retained with a reason, not rewritten. A manifest contains schema/source snapshot version, source key set and per-key digests, account set, copy status, aggregate digest and validation findings. It is never an active-authority marker. No new production dependency is needed; use browser-provided primitives for digests.
2. Take an origin-wide enumeration of relevant namespaces, sorted by **complete key**, with exact raw values. Capture all accounts, unscoped legacy keys and account pointers. Re-enumerate and byte-compare before staging and after staging; any source mutation produces a stale/quarantined copy, not a verified result. Because `localStorage` has no transaction or cross-tab lock, even a stable double-read is a *snapshot observation*, never proof that future writes stopped. No Stage E logic may write, repair, migrate, delete, or normalize a source key.
3. Validate pure record structure, semantic identities and reference graph from captured raw bytes: artifact/slot/control/head; every pending recovery across **all campaigns for a slot**; candidate and attempt edges; v6 group and migration receipt/source; full account profile/consumer links; and first Soundings witness against its independent first durable artifact and subsequent snapshot. Record per-account and origin-level blockers. Preserve raw records for unknown versions or malformed JSON. Do not turn an invalid record into a default profile or a playable partial campaign.
4. Write staged records and manifest in a bounded IndexedDB transaction or explicit multi-transaction provisional generation that cannot be marked `verified` until count, keys, bytes and digests are read back after the transaction. Abort/quota/blocked-upgrade leaves v1 publication stores and legacy keys unchanged and no verified manifest. An exact same-source retry returns the same verified generation without overwriting conflicting bytes; a changed source creates a separate generation or explicit stale result. Never overwrite a staged record or v1 authority on an ID collision.
5. Close and reopen the database, then independently read and compare the full manifest and every staged raw record. Test restart, source change during enumeration/commit, concurrent tabs, quota, abort, blocked upgrade, malformed/unknown records, missing first witness artifact, cross-slot competing recovery, non-head/fork and multi-account data. Mark `verified` only for a complete inert snapshot with no copy/readback discrepancy; semantic blockers stay explicit and prohibit activation. No app boot, load or save caller consults this manifest in Slice E.

If v1 stores already contain the same account/campaign identities, Stage E does not merge or prefer either store. Record that as a divergence requiring later explicit reconciliation. A copied malformed key is retained evidence but not validated authority. Copy success is permitted to be `verified-with-blockers` only if that status is unambiguously ineligible for activation; no code may interpret it as ready.

## Later activation, caller and rollback gates

Activation requires a separate versioned canonical schema that can represent **all** retained families, non-head/fork artifacts and slots, pending recovery/attempt and account consumer state; materialization must validate every source relationship without minting new IDs or replacing nested authority. The implementation must stop or fence `localStorage` writers across tabs, re-enumerate source against the staged generation, resolve every blocker and existing-v1 conflict, then use a single account-scoped authority selection commit. A stored marker is only authoritative when its complete canonical records and exact identities are verified after database close/reopen and browser restart. No wall-clock "latest" choice resolves divergent stores. Stale tabs must fail closed and refresh rather than write to legacy keys or overwrite a newer selected head.

`App.tsx` synchronously bootstraps profile/slots, repairs account-wide recoveries, prepares a new campaign, publishes saves, updates consumers, loads, deletes, resets and changes sessions. `saveManager.ts`, `accountProfileManager.ts`, `newCampaignAttemptCoordinator.ts` and launcher reset/delete participate. Those callers need explicit async loading/saving and pending/error state before activation; a helper-only IndexedDB test is insufficient. In particular, `resetLocalAccount` and `deleteLocalAccount` currently clear v7/v6/obsolete saves and profile but do not enumerate attempt keys or the new database. Their future semantics must atomically fence all stores or leave a recoverable tombstone so staged/canonical data cannot revive a deleted or reset account. Credentials remain launcher-owned.

Before any old-key retirement: demonstrate user-controlled full export and restore of canonical campaign/account data plus necessary provenance; test rollback to exact old verified bytes, including a failed or interrupted activation and divergent-source quarantine. Old source keys remain readable and unchanged during copy and initial activation. Retirement needs its own approved proof after rollback/export closure; no candidate/artifact/history garbage collection is included here. Quota is dynamic and browser-specific: report `navigator.storage.estimate()` as an estimate, injection results and exact serialized bytes; fail safely when denied, evicted, blocked or unavailable. A 1,000-save plus second-campaign workload is an engineering acceptance scenario, not a product count limit or the old 5 MiB model.

Later native-browser acceptance must cover at least Chromium and Firefox on this app origin: (1) multi-account migration with a non-head slot/fork, pending recovery/attempt and applied Soundings witness, close/reopen/restart, exact artifact/profile/consumer/witness readback and no old-key mutation; (2) concurrent tabs with stale legacy writer, source change during copy, blocked upgrade, injected quota/abort and failed activation, proving prior verified authority remains loadable and export/rollback works. Repeat the long-running save scenario in both browsers before any backend-capacity or combat gate is claimed.
