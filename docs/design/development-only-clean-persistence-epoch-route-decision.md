# Development-Only Clean Persistence Epoch Route Decision

Date: 2026-09-29. Inspected clean synchronized `master` at `18ef8008e398cf13c316374a403d7069e7fedc7d`. Unversioned owner-policy decision supporting planned `DEV-0.7.1`. Game `0.1.1-prealpha`, playability `INTEGRATED_LOOP`, accepted `DEV-0.7.0` unchanged.

## Decision and scope

**CLEAN_DEVELOPMENT_EPOCH_ROUTE_ACCEPTED; IMPLEMENTATION_AND_ACTIVATION_HELD.** The owner confirms that the existing Sites deployment is development/testing only, has one user, and no pre-cutover browser-local account, credential, session, campaign, save, history, migration record or other test data must survive. A deliberate one-time reset and fresh registration/campaign are accepted. This supersedes the earlier requirement to prove that every old same-origin writer has been technically excluded before beginning the clean epoch. It does not assert that new code can terminate an already-open old script. The owner will close/reload all development tabs as an operational cutover condition; existing obsolete writes are never promoted into new authority.

Do not implement a legacy importer, raw-copy reconciliation, source recensus, export/import, backward-save compatibility, old-save recovery, or a two-stage old-client handshake solely for this development data. Slice E/F's inert copy/canonical stores and their historical evidence can remain in the codebase without being selected by the new app; removing them is separate cleanup. Do not inspect an archived deployed bundle solely to justify old-data preservation. The previous literal old-writer impossibility remains a valid technical observation, but it is no longer the product activation gate for this sole-user development cutover.

The clean epoch must give new data a distinct authority boundary. Use the existing transactional publication design as the starting implementation, but select a fresh versioned IndexedDB database name for the live epoch, rather than activating the old `lineage.campaigns` v2/v3 legacy-copy database. Keep account credentials, session/active selection and any small localStorage convenience keys in an epoch-specific namespace; prefer IndexedDB for durable account/profile and credential ownership where an atomic account operation requires it. A session pointer is only a hint and must be validated against the durable account. New code must never fall back to v6/v7 legacy saves, old profiles/attempts, the inert canonical copy, or old launcher keys when new-epoch read/open fails. Old scripts may still write obsolete localStorage if the owner reopens one, but those bytes cannot select or overwrite new authority. The versioned database and keys are a small non-interference boundary, not a claim of general protection against arbitrary same-origin code or a substitute for closing tabs.

## Cutover and acceptance sequence

1. Build and validate the new repository and complete async real-caller conversion while the live old app remains unchanged. A store helper alone is not an activation. Keep the old app's current data untouched until the new build is ready.
2. Before the first new-epoch launch on each used origin/browser profile, the sole user closes every open development tab/window for that origin, including any local Vite tabs, and stops the local server when relevant. Deploy the built new app, deliberately clear obsolete development site data for that exact origin/profile, then launch the new build and start a new account and campaign. The hosted Sites and `127.0.0.1:5173` origins have separate storage; clearing one does not clear the other. The final reset procedure must name the exact affected origins and ensure it cannot erase data created after the new epoch starts. Do not perform this reset during this decision pass.
3. The new app must fail closed on blocked IndexedDB upgrade, unavailable/quota errors, malformed account or campaign records, stale head, and incomplete recovery. It must not silently create a default playable account or empty slot list from a failed read. Surface retry/repair through a reachable caller. Real App and launcher paths must await successful durable readback before showing save, new-campaign, retirement, reset or deletion success.
4. Accept post-epoch durability only after native browser restart/retry/conflict and long-running workload checks preserve legitimate world, lineage, Chronicle and history state; all accepted non-head/fork artifacts; account/profile and attempt relationships; independent first Soundings witness and artifact provenance; and recoverable pending operations. Account reset/delete must be durable and idempotent across interruptions, with auth/session handling consistent with the same account transition. Quota/eviction behavior and user-controlled backup/restore must address **new** data. The old 5 MiB localStorage result is a failure of the old backend, not a product data ceiling.
5. A rollback to a pre-epoch build must not be used to edit a new-epoch account. Rollback that preserves new data requires an epoch-compatible build and exact readback; otherwise keep the new database untouched and restore the new build. Later new-epoch versions need version/transaction checks against stale new-epoch tabs; publication's expected-head compare-and-swap is a foundation, not whole-account conflict coverage.

## Implementation order and stop conditions

The next bounded checkpoint is **DEV-0.7.1 Slice G1 - Clean-Epoch Transactional Account Store Extension**. Extend the isolated IndexedDB owner to open a fresh epoch database and durably represent account profile/identity, credential ownership, active-account selection rules, attempts and recovery/consumer relationships needed by later callers. Preserve the v1 artifact/control/slot/witness atomic publication and exact readback. Keep the legacy copy/canonical owners inert. Prove registration and account identity, stale revision, transaction abort, quota/unavailable, restart/readback, retry and malformed-record boundaries with synthetic native-browser data. Do not import the new owner into App/launcher or clear browser data in G1. If one coherent transaction surface exceeds an `S` slice, split account registration/profile from attempt/recovery at a durable tested checkpoint rather than weakening atomicity.

After G1, use bounded async caller slices for save/slot/recovery, profile/attempt/lifecycle, launcher/auth/session/reset/delete and App bootstrap/actions, followed by an end-to-end activation and independent long-run/two-browser acceptance pass. The exact package boundaries may be refined from implementation evidence, but no slice may claim live cutover while a real caller still reads/writes legacy authority. Combat admission and planned parent `DEV-0.7.1` acceptance remain held until the post-epoch capacity and ordinary-path gates pass. No game-version decision follows from this route change.
